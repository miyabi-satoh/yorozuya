# セッションの再起動

## 仕事

再起動の目的は、コンテキストが枯渇して性能が落ちる前に、会話ログを引き継いで新しいセッションに移ること。

**判断はこのセッションが持つ。** スクリプトが引き受けるのは、後戻りできない連鎖（`/exit` から資料を読ませるまで）と、聞きに行くきっかけを出すだけの見張り（[watch.md](watch.md)）。
対象の状態は画面から読み取らず、**対象に聞く**。返信は自動で届く。
画面から読むのは、聞きに行くきっかけと、聞いても届かないとき（依頼が送信されずに残っている、ダイアログで止まっている）にとどめる。

知らせや状況に応じて、次の別ファイルに進む。

- コンテキストの見張りを始める・知らせを受ける: [watch.md](watch.md)
- 放置で大きくなった会話を `/clear` して続ける（`IDLE` の知らせ）: [idle-clear.md](idle-clear.md)
- 自分自身（Yorozuya）を再起動する: [restart-self.md](restart-self.md)

## やらないこと

- 対象に資料を書かせる — 会話ログは呼び出し元が自動で抜き出す（手順4）。対象が書くのは短い返信だけ。
- 対象の状態を画面から読み取って決める — 対象に聞く。画面から読むのは、聞きに行くきっかけと、聞いても届かないときだけ。
- 返信をポーリングする — 返信は自動で届く（手順3）。
- `blocked` の対象に依頼を送る — ツール呼び出しの切れ目まで読まれない。ユーザーにペインで答えてもらう（判断の基準）。
- `--allow-background` で自分の照合だけを素通りさせる — シェルは動いたままなので、`/exit` の確認画面でユーザーに手で答えてもらうことになる（手順5）。
- 状態メモや新セッションの応答の中身をユーザーに写す — ユーザーはそのペインで見ている（手順7）。
- 対象のコンテキスト使用量を、外からトークンで数える — 理由は「知っておくこと」。

## 出力

- 新セッションに渡す資料（返信の状態メモ＋抜き出した会話ログ）。スクリプトがその前に進め方をつないだ `-with-guide.md` を作って渡す。
- ユーザーへの報告: 打った手と成否（再起動したか・resume の ID・新セッションが何%で始まったか）。

## 終わる条件

新セッションが資料を読み始めた（手順6で `working` か、資料を読んだ応答が出た）のを確かめ、報告した。対象が「止められない」と返したときは、理由をユーザーに伝えたところで終わる。別ファイルの手順（[idle-clear.md](idle-clear.md)・[restart-self.md](restart-self.md)）は、そちらに書いた終わり方に従う。

## 止まる条件

次のときは推測で埋めずに止まり、ユーザーに聞く。

- 承認が要る操作の手前: 対象が `blocked`（承認や選択式の問いの待ち）。ユーザーにそのペインで答えてもらう。
- 承認が要る操作の手前: `/exit` の後や起動の時に確認画面・ダイアログ（フォルダの信頼、MCP サーバーの承認、worktree を残すか、バックグラウンドの処理）が出た。ユーザーにペインで選んでもらう。
- 承認が要る操作の手前: 入力欄に書きかけがある。ユーザーが送信するか消すまで待つ。
- 承認が要る操作の手前: `config.local.json` の `confirm` が `true` で、見張りの知らせから再起動や `/clear` に進むとき。
- 必要な情報が分からないとき: 資料を読ませる依頼が送信されたか、手順6の条件で決められない。Enter を送らずにユーザーにペインを見てもらう。

## 手順

1. `herdr agent list` で対象のペインID・Herdr の名前・セッションID（`agent_session.value`。手順4で使う）を引く。
   `ListAgents` で自分の名前と対象の名前を引く（`yorozuya-XX` の XX はセッションごとに変わる。引き継ぎ資料の名前は使わない）。
   `ListAgents` の名前は Herdr の名前とは別物で、`herdr agent list` の `terminal_title_stripped`（`<マシン>/<名前>` の形）の名前の部分と同じ。

2. 手順1で見た `agent_status` が `blocked`（承認や選択式の問いの待ち）なら、依頼を送らずユーザーにそのペインで答えてもらう
   （「判断の基準」参照）。`working`／`idle` なら `SendMessage` で依頼を送る
   （対象に何か書かせるのではなく、区切りの確認だけを求める短い依頼）。
   ```
   SendMessage({ to: "<対象の名前>", message: "<依頼文>" })
   ```
   資料は書かせない。**会話ログは呼び出し元が自動で抜き出す**（手順4）。対象が書くのは短い返信だけ。
   SendMessage はツール呼び出しの切れ目で読まれるので、`working` 中でも自然に届く（追加の催促は要らない）。
   ただし1回の長いツール呼び出し（前景のサブエージェント待ちなど）の最中は届かない。

   依頼文に入れること。
   - 再起動の理由と、再起動後も同じプロジェクトで作業を続けること
   - **今すぐ中断できる粒度まで進めたら返信すること。PRやタスクの完了までは待たない。**
     目安は、実行中のコマンドの出力待ちが済む・今編集しているファイルの編集が一区切りつく、程度。
     次のファイルの編集やコミットには進まず、その手前で返信する。
     「続けますか」のような問いを自分で出したら、その返事（ユーザーからの `y` 等）を待たずに、まずこちらへ返信すること。
     ここを緩く書くと、対象がユーザーの即答（デスクトップアプリ経由など、ペインの外からの回答も含む）で
     次の大きな項目に入ってしまい、区切りをいくつも通り過ぎてから返信が来ることがある
     （2026-09-23 あるプロジェクトで実際に発生、41%→62%まで伸びた）
   - **返信は `SendMessage` ツールで、呼び出し元の名前（`ListAgents` に出る自分の名前）宛てに送ること。** これを書かないと、対象は自分の会話にテキストで答えるだけで済ませてしまい、返信が呼び出し元に届かない（実際に起きた事故）。
   - 返信に含めてほしいこと
     - 状態: 作業の途中（ユーザーの新しい指示が無くても次の一手に進むつもりだった。何をどこまで済ませ、次に何をするか）／ユーザーの答えや操作の待ち（ユーザーへの問いや頼んだ操作の文面と選択肢をそのまま。ダイアログで聞いたかテキストで聞いたかも）／指示待ち（次に何をするかをユーザーが決める）のどれか
     - 再起動でバックグラウンドの処理はすべて止まる（シェル・Monitor・バックグラウンドのサブエージェントに加えて、`ScheduleWakeup` などの予約タスクも対象。
       サブエージェントと予約タスクは手順5のモードラインの照合で拾えないので、自己申告に頼るしかない）。
       立ち上げ直せばよいものがあれば、その手順。書いたら自分で `TaskStop` などで止めること。サブエージェントも止める（「止まってよい」と書くだけで残すと、`/exit` の後にハーネスの確認画面が出て、ユーザーに手で答えてもらうことになるとみられる。2026-09-26 にそう見える事故があった）
     - `EnterWorktree` で入った worktree にいるなら、`ExitWorktree` の `keep` で抜けてから、worktree のパスとブランチを返信に書くこと（新セッションが `EnterWorktree` の `path` で入り直せるように）。入ったままだと `/exit` の後に worktree を残すか消すかの確認画面が出て、ユーザーに手で答えてもらうことになる。消す側を選ぶと、worktree のブランチのコミットや未コミットの変更が失われうる。モードラインにも出ないので、自己申告に頼るしかない（2026-10-01 に実際に起きた）。`ExitWorktree` はユーザーに頼まれたときに使う道具なので、対象がユーザーに確かめてから抜け、返信が遅れることがある
     - 今止めるとまずい処理が走っているなら、その旨だけ返信すること（この場合ほかは書かなくてよい）
   - このプロジェクトの全体の流れの置き場（roadmap の文書・外部のノートのページ・issue など、形は問わない）があれば、返信の前に今の状態へ直しておくこと
     - 置き場への書き込みが外向きの操作になるなら（issue・外部のノートなど）、そのプロジェクトの決まりどおりに確かめる。直せなければ、ずれを返信に書く
     - 置き場が CLAUDE.md・AGENTS.md・記憶から辿れなければ、辿れる1行を足す（足してよいかはユーザーに聞く）。公開しているリポジトリで置き場が非公開なら、公開するファイルではなく、CLAUDE.local.md や記憶に足す
     - 全体の流れと呼べるものが無い規模なら省いてよい。流れはあるのに置き場が無ければ、ユーザーに置き場を聞く

   全体の流れを置き場に直させるのは、会話ログの抽出が今の会話の範囲にとどまるから。
   会話に出てこなかった大きな流れ（中長期の作業のうち、今のセッションが触れていない部分）は会話ログに入らず、置き場に無ければ再起動のたびに細る。
   置き場の形はプロジェクトの規模で違うので決め打ちしない。

3. 返信を待つ。**ポーリングしない。** 返信は自動でこの会話に届く。
   何も返ってこないまま気になるなら `SendMessage` の `notify_when_idle` を使う。

4. `scripts/extract-transcript.mjs <旧セッションID> --out <出力先>` で、旧セッションの会話ログ（ユーザー・アシスタント・他のセッションの発言テキストだけ。ツール実行結果・thinking・skill の本文は含まない）を抜き出す。
   旧セッションIDは手順1で引いたもの。`/exit` の前でも後でも実行できる（トランスクリプトはセッションの生死と関係なくファイルに残る）。
   手順2の返信（状態・置き場・止めるものの一言）を先頭に、会話ログを続けて1つのファイルにまとめる。これが新セッションに渡す資料になる。進め方（`after-restart.md`）は、手順5のスクリプトが資料の前につないだ別のファイル（資料の `.md` を `-with-guide.md` に替えた名前）を作って渡すので、資料には足さない。
   **会話に出た秘密情報（貼ったトークン・パスワードなど）は、抜き出した資料にもそのまま残る。** 要約を挟まない分、伏せる判断も挟まらない。心当たりがあれば渡す前に見て消す。
   旧セッションが最初の発言で前の資料を読んでいれば（再起動や `/clear` の後のセッション。このスキルの依頼の定型で見分ける）、抜き出しはその資料を2万文字までに収めて末尾につなぐ。`@` で読ませた中身は抜き出しに入らず、つながないと前の経緯が落ちるため。上限は、つなぐたびに資料が膨らみ続けるのを止めるため。前の資料の状態メモと会話ログを先に残し、そのまた前の世代を古い側から省く。前の資料だけで上限を超えれば、頭（状態メモ）と末尾（最後のやり取り）を残して中を省く。ユーザーが自分で `/clear` したセッションなど、最初の発言が依頼の定型でなければつながらない。要るなら、プロジェクトの JSONL を更新日時の順にさかのぼって手でつなぐ。

5. `scripts/restart.mjs <pane> <name> <資料の絶対パス>` を実行する。
   終了・起動・読み込みを一息で行う。**ターンをまたがせない。**

   `/exit` を送る前に、対象のモードライン（画面の最終行、`⏵⏵ auto mode on · N shells · ← for agents` の形）を読み、
   バックグラウンドのシェル・Monitor が見えていれば SKIP する。**対象の自己申告は当てにしない。**
   自己申告と実際のハーネスの追跡が食い違うことがある（2026-09-11・2026-09-23 に別プロジェクトで実際に起きた）。

   SKIP になったら、対象に「モードラインに◯件動いていると出ている」旨を伝えて確かめてもらう。
   **「止めてよい」という答えが返ったら、対象自身に `TaskStop`（や相当する手段）で止めてもらってから、
   モードラインが消えたのを確かめて `--allow-background` を付けずに同じ引数で呼び直す。**
   ここで `--allow-background` を使って自分の照合だけを素通りさせてはいけない。シェルは実際には動いたままなので、
   結局 `/exit` 自体のハーネス側の確認画面（`Background work is running`）に引っかかり、
   ユーザーに手で答えてもらう羽目になる（2026-09-23 に実際に起きた。今日の直しの目的が「ユーザーが選ばずに済むように」だったのに、
   同じ選択を最後で頼むことになっては本末転倒）。

   `--allow-background` を付けてよいのは、対象が「セッションを終えても動かし続けたい」と明言したもの
   （detached な dev サーバーなど、対象自身が独立したプロセスだと確認して報告したもの）だけに限る。
   その場合でも `/exit` 自体の確認画面は避けられないことがあるので、対象に「動かしたままにするので、
   確認画面が出たら『Move to background and exit』を選んでほしい」と伝えておくか、
   ユーザーにその旨を伝えて選んでもらう。

6. 資料を読ませる依頼（`@<資料>-with-guide.md 前セッションの引き継ぎ資料です。…`）が送信されたかを確かめる。`OK` は、Herdr が依頼の文と Enter を送ったところまで。claude が受け取って動き出したかは見ていない。Enter だけが落ちて、依頼が入力欄に残ったことがある（原因は分かっていない）。
   ```
   herdr agent wait <name> --until working --until blocked --timeout 30000
   ```
   返ったもので分ける。
   - `working` — 資料を読み始めている。手順7へ。
   - `blocked` — `herdr agent read <name> --source visible` で画面を読む。新セッションが出した問い（選択式の問い）や、ツールの実行の許可なら、依頼は送信されている。手順7へ。起動の時に出るダイアログ（フォルダの信頼、MCP サーバーの承認など）なら、依頼は送信されていないかもしれない。Enter を送らずにユーザーにペインを見てもらう。
   - `timeout` のエラー — `herdr agent read <name> --source visible --format ansi` で画面を読む。入力欄が空か薄字（`ESC[2m`）のサジェストだけで、資料を読んだ応答が会話に出ていれば、依頼は送信されている（指示待ちの新セッションは、短いターンで `idle` に戻る）。手順7へ。そうでなければ、次の両方に当てはまるときだけ、`herdr agent send-keys <name> Enter` で送り、もう一度待つ。
     - 入力欄にあるのが依頼の文だけで、薄字（`ESC[2m`）のサジェストではない。長い依頼は末尾しか見えない
     - 候補のメニューも、ダイアログや選択式の問いも出ていない

   どれにも当てはまらないとき（入力欄が上の条件に合わない、2回目も時間切れ、ほかのエラー）は、Enter を送らずにユーザーにペインを見てもらう。

7. 結果を報告する。旧セッションID は `resume:` として出力の末尾に出る。
   報告するのは打った手と成否（再起動したか・resume の ID・新セッションが何%で始まったか）まで。状態メモや新セッションの応答の中身（出し直した問い・作業の状況）は写さない。ユーザーはそのペインで見ている。

### 判断の基準

**区切りかどうかは対象が決める。** 依頼文に「今すぐ中断できる粒度まで進めたら返信」と書き、あとは待つ。
`idle` は「入力を待っている」だけで作業の区切りとは別物（返事待ちを4件抱えたまま idle だった例がある）。

**返信の形を決めつけない。** 「READY」とだけ返す相手もいれば、報告を添える相手もいる。
読んで判断する。過去に申告の形を1つに決めつけて、拾えないまま黙って待ち続けた事故がある。

**名指しの指示はそのまま流す。** ユーザーが「このセッションを再起動して」と言ったら、それが承認にあたる。
確認を取り直すのは、こちらから提案するときだけ。

**対象がテキストの問いかけを表示したまま止まっていても進める（`agent_status` が `idle` のもの）。** ユーザーは問いの存在を承知のうえで指示していることがあり、「先に答えますか」と聞き返せば答える方向へ誘導することになる。宙に浮いた問いかけは資料に残り、新セッションが出し直す。

**ただし選択式の問いや承認ダイアログ（`blocked`）は別。**（再起動した新セッションが出し直した選択式の問いもこれに当たる） ダイアログで完全に止まっているので、`SendMessage` を送ってもツール呼び出しの切れ目まで読まれない。手順2で `blocked` を見た時点で送らずにおく。スクリプトも pre-flight で止まる。ユーザーにペインで答えてもらう。

### 詰まったとき

- **対象が「止められない」と返してきた** — 旧セッションは無傷。理由をユーザーに伝えて終わる。その処理が済んでから改めて提案する。
- **返信が来ない** — 依頼は届いている。後から返ってくることがある。急ぐならペインを見る。
  依頼が入力欄の下にキューとして残っていれば、対象のターンがまだ終わっていない。急ぐならユーザーにペインで Esc を押してもらう（ターンが止まり、キューの中身がすぐに送られる）。
- **FAIL で確認画面** — `/exit` の後の終了確認はユーザーにペインで選んでもらう。終了した後の戻り方はメッセージに書いてある。
  自己申告で「バックグラウンド処理はなし」と言われていても、`ScheduleWakeup` などの予約タスク（モードラインに出ない）が
  残っていて確認画面（`Background work is running` → `scheduled task ...`）が出ることがある（2026-09-23 に別プロジェクトで実際に発生）。
  これはシェル・Monitorの食い違い（手順5のモードライン照合）とは別物で、今のところ画面から検知する手段が無い。
  ユーザーに内容を伝えて選んでもらう。「Runs once in 0s」のようにほぼ即時実行なら、止めても実害は小さいことが多い。
  `EnterWorktree` で入った worktree に対象がいたままなら、`Exiting worktree session`（Keep worktree / Remove worktree）が出る（2026-10-01 に実際に発生）。ユーザーに Keep を選んでもらい、シェルに戻って名前が外れたのを確かめてから `herdr agent start`、起動したら `@<資料>-with-guide.md` を送る。渡す `-with-guide.md` に worktree のパスとブランチが無ければ、送る前にそちらへ足す（`-with-guide.md` は `/exit` の前に作られるので、元の資料に足しても届かない）。
- **FAIL で `/exit` を送った後に止まった** — claude が終了してシェルに戻った後は、**同じ引数で再実行しても通らない。** エージェントのいないペインは pre-flight で SKIP になる。メッセージに書いてある手順で手で起動し直す（名前が外れたのを確かめてから `herdr agent start`、起動したら `@<資料>-with-guide.md`。または `claude --resume <ID>` で元の会話）。確認画面でキャンセルして claude が動き続けているなら、何も変わっていないので再実行できる。
- **対象が `blocked` で依頼が届かない** — 直前の再起動で新セッションが出した問い（出し直した問いや、状態を聞く問い）や、再開した作業の権限の確認に、まだ答えていないことがある。ユーザーにそのペインで答えてもらってから、手順1からやり直す。
- **FAIL で起動の段が `agent_pane_busy`** — `/exit` の後にシェルへ戻ったのを確かめてから起動しているので、旧セッションは終わっている。Herdr がそのペインをまだ使用中と見ているだけ。**まずペインを見る。** claude が上がっていれば、確認やダイアログが出ていないか見て、出ていれば答えてもらってから `@<資料>-with-guide.md` を渡す。シェルのプロンプトに戻っていれば、メッセージに書いてある手順（名前が外れたのを確かめてから `herdr agent start`、起動したら `@<資料>-with-guide.md`）で起動し直す。
- **SKIP で止まった** — まだ何も変えていない。メッセージのとおりに直して再実行する。資料は絶対パスで空白なし、名前は Herdr の規則（先頭は小文字・英数と `_` `-`・32字以内）、ペインIDと名前は `herdr agent list` で引き直したものであること。
- **SKIP で入力欄に書きかけ** — ユーザーがそのペインで打っている最中かもしれない。`/exit` を送ると書きかけの末尾につながり、書きかけごと送信される。対象に頼んでも消せない（入力欄はユーザーのもの）。ユーザーに、送信するか消すまで待つと伝え、済んだら同じ引数で呼び直す。入力欄を読めないとき（書きかけが長く、上枠が画面の外に出ているなど）も同じく止まるので、ペインを見て確かめる。
- **SKIP でモードラインの食い違い** — 対象の自己申告と、実際にハーネスが追跡しているシェル・Monitor の数が合っていない。対象に伝えて確かめてもらう。「止めてよい」なら対象自身に `TaskStop` で止めてもらい、モードラインが消えたのを確かめてから `--allow-background` を付けずに呼び直す。`--allow-background` は、対象が動かし続けたいと明言したものにだけ使う（詳しくは手順5）。
- **FAIL で「新ペインは開いたまま残した」（自己再起動）** — 起動が失敗した。信頼ダイアログや確認がそのペインに出ていないかユーザーに見てもらう。答えてもらったら、**必ず先にそのペインを閉じてから**同じ引数で呼び直す（閉じずに呼び直すとペインが増える）。ペインを閉じないのは、答えようとした画面を消さないため。
  メッセージには Herdr 名の状態も書いてある。「握ったままで、外せなかった」と出ていたら、**生きているこのセッションが無名で、名前は残した新ペインを指している**。書かれた順に手で戻す（まず新ペインの名前を `--clear`、通らなければペインを閉じて名前が外れるのを待ってから旧ペインに付け直す）。閉じた直後は名前の解放に数秒かかるので、呼び直しで「名前 … が使用中」の SKIP が出たら少し待ってもう一度。
- **FAIL で「ペインは分割できたが ID を読み取れない」（自己再起動）** — Herdr の出力の形が変わった可能性。新ペインが残っているので手で閉じる。閉じずに呼び直すとペインが増える。
- **SKIP で「ペインの cwd を取れない」（自己再起動）** — Herdr が cwd を返さなかった。`herdr pane current --current` で Herdr 側の状態を確かめる。

### 知っておくこと

- 再起動した新セッションの進め方は、`after-restart.md` にある。2つのスクリプトは、これを資料の前につないだ別のファイル（資料の `.md` を `-with-guide.md` に替えた名前）を作り、それを `@` 参照で渡す。資料そのものは書き換えない（本文をプロンプトに入れると長く、2つ目の `@` 参照で添えると送信されなかったため。決めごとの理由は `scripts/lib/prompts.mjs`）。資料に書かれた状態から続け、再起動を知らせる問いは出さない。再起動したことは、自己再起動では新セッションが、ほかは呼び出し元が報告する。
  進め方には、Claude の週次枠がハイペースで Codex に余裕があるときだけ、作業を Codex に回すよう一文を足す（`scripts/lib/pace.mjs`。数字は weekly-pace スキルのスクリプトで、呼び出し元の自分のペインから読む）。各セッションに毎回のプロンプトで差し込む hook を置かず、再起動のたびに入れる。
  新セッションがダイアログ（AskUserQuestion）で問いを出し直すと、答えるまでそのペインは `blocked` で、見張りからは使用率を読めず、`herdr agent prompt` も届かない。
- 自己再起動には、手順6にあたる確かめが無い。新しいペインの入力欄に依頼が残っていたら、ユーザーが Enter を押す。
- 実行中にこのセッションが終わると、スクリプトも止まり、対象が終了したまま残ることがある。
  旧セッションID は最初のログに出ているので `claude --resume <ID>` で戻せる。
- 対象のコンテキスト使用量を、外からトークンで数えない。モデルごとに違う上限をこちらが決め打ちすることになる。
  見張りが読むのは、ステータスラインが上限を踏まえて出した使用率。
- 見張りを走らせていなければ、**他セッションの増加に自分で気づく契機は無い**。ユーザーの指示か対象の申告から始まる。

## 合格条件

- 人が見る: 資料の先頭に対象の返信（状態メモ）があり、会話ログが続いている。報告が打った手と成否にとどまり、状態メモや新セッションの応答の中身を写していない。
- 機械が見る: `restart.mjs` が `OK` を返し、`herdr agent list` の対象ペインのセッションIDが旧セッションIDと違う。
