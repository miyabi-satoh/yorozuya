# 机上検査

## 設定

ここだけを変えれば、手順の全体に効く。

- **領域を読む・確かめ直すサブエージェントのモデル: `opus`**（Claude Code の Agent ツールの `model` に渡す値。`sonnet`・`opus`・`fable` など）。
  - 理由: 調べものとレビューは、Sonnet か Opus が勧められている。ソースコードの欠陥探しの社内の試しでは、Opus が率いて Sonnet が読む組で、Opus だけと同じほどの成績だった。Fable はトークンあたり Opus の2倍で、モデルを上げるより確かめ直しを入れるほうが安く効く（Anthropic「Which Claude model should you build with?」）。
  - 率いる側（このセッション）のモデルは変えない。モデルを切り替えると、キャッシュの作り直しと戻す手間がかかるため。
- **最初に並べる数: 2**。2回目からは、手順5で測った使用量から決める。
  - 理由: 一度に並べたサブエージェントは、同じ5時間枠を同時に使う。11 を並べて、枠が尽きた時点で全部が同時に失敗したことがある。最初の組を小さくすれば、1つあたりの使用量を測ってから数を決められる。

## 仕事

リポジトリのソースを読むだけで、利用者が実際に踏む欠陥（データを失う・止まったまま戻れない・決めごとや文書と食い違う・OS ごとの落とし穴など）を洗い出し、確かめ直したものだけを、読む人が次に何を直すか決められるレポートにして出す。

## やらないこと

- ビルド・テスト・実行・実機での確かめ — 机上検査は読むだけ。実機で決まる所は「実機で確かめたいこと」に書き、確かめるのは別の作業にする。
- 見つけた欠陥を直す — 直すかどうか・どの順に直すかは、レポートを読んだ人が決める。
- 書き方・名前・リファクタ・テストの不足・リンターが拾うものを指摘に入れる — 利用者が踏むものではない。
- 理論上ありうるだけで、実際の操作や環境で起きる道筋が無いものを指摘に入れる — 直す候補に挙げるのは、実際に起きた・利用者が普通に踏む問題だけにする。
- 確かめ直していない指摘を、そのままレポートに載せる — サブエージェントの指摘は、自信のある書き方で間違っていることがある。

## 出力

- アーティファクト1枚: 「<アプリ名> 机上検査レポート」。組み方は `references/report-template.html`（上に結論と件数、重さ順の節、各指摘に 起きること・理由・確かめ方・場所・直す方向、OS と確かめの度合いのタグ、「実機で確かめたいこと」「確かめて問題なかったこと」、後で書き足す対応の状況のタグ）。
  - 読むのは人なので、日本語で書く。内部の名前でなく、利用者が見る画面と操作で何が起きるかから書く。利用者の指示ファイルに、読み手に向けた文章や画面の文言の決まり（skill を含む）があれば従う。
  - アーティファクトを出せないエージェントでは、同じ HTML をファイルに書いてブラウザーで開く。
- 返答: アーティファクトのリンク、件数、いちばん重いものを1〜2文。

## 終わる条件

レポートを出し、`scripts/check-locations.mjs` が終了コード 0 で通り、返答でリンクと結論を伝えた。

## 止まる条件

次のときは推測で埋めずに止まり、ユーザーに聞く。

- 必要な情報が分からないとき: 検査の対象（どのリポジトリ・どのブランチ）が決まらない。作業フォルダに未コミットの変更があり、それを含めて読むかが分からない。
- 指示や資料が食い違うとき: 設計の文書と決めた記録（ADR など）が互いに食い違い、どちらを「意図した動き」として読むかで指摘の重さが変わる。
- 承認が要る操作の手前: 使用量の枠が尽きかけていて、続けると残りの作業（ほかの作業を含む）が止まる見込みのとき（手順5）。

## 手順

1. 対象を決める。リポジトリ・ブランチ・コミット（短い SHA をレポートに書く）、検査の時期（「最初の公開の前に」など。ユーザーが言わなければ「次の版を出す前に」）、大事な OS。作業フォルダが clean かを確かめる。
2. 意図した動きの資料を集める。リポジトリの指示ファイル、設計の文書・決めた記録・仕様、マニュアル、配り方の設定（パッケージのマニフェストなど）。リポジトリの外に仕様や決めごとの置き場があれば、利用者の指示ファイルから辿る。
3. 領域に分ける。`git ls-files` の全部を、1つのサブエージェントが1行ずつ読み切れる大きさの領域に割り振る（目安は、機能のまとまり・層ごと。画面・文言とマニュアル・起動と配り方も、それぞれ領域にする）。割り振りから漏れたファイルが無いかを、一覧と突き合わせて確かめる。生成物・ロックファイル・画像は読まない側に入れる。
   - 領域をまたいで1か所で見たほうがよい点検（すべての入口の権限の表と文書の突き合わせ・保存するすべての設定で知らない値が残るか など）は、どれか1つの領域の受け持ちにする。
4. 領域ごとの依頼文を `references/area-prompt.md` から作る。領域の「見るもの」には、その領域の具体的な仕組みを5〜10個挙げる（「復元で表を写す順とトリガー」のように）。同じリポジトリで前に机上検査をしていれば、そのレポート（アーティファクト）を読み、前に見つかった種類を見るものに足す。
5. サブエージェントを組に分けて流す。モデルは「設定」の値を Agent ツールの `model` に渡す。
   1. 流す前に、5時間枠と週次枠の使用量を確かめる（weekly-pace の skill があれば `claude-usage.mjs --force` の `primary`（5時間枠）と `secondary`（週次枠）の `usedPercent`・`resetsAt`。`--force` を付けないと15分前までの値が返る）。取れなければ、2つずつ順に流す。
   2. 最初の組は「設定」の数だけ流し、終わったら使用量をもう一度読んで、1つあたりの増え方を出す。
   3. 次の組の数は、枠の残りに収まる数にする（枠の 85% を超えない見込みの数。ほかのセッションも同じ枠を使うので、使い切らない）。
   4. 枠で失敗したサブエージェントは、すぐに流し直さない。5時間枠のリセットの時刻（`primary.resetsAt`）まで待ち、失敗した領域だけを流し直す。Claude Code では、途中まで読んだサブエージェントに SendMessage で続きを頼むと、読んだ分を捨てずに済む。
   5. 残りの作業に足りないほど週次枠が尽きかけていれば、止まる条件のとおりユーザーに聞く。
6. 指摘を1件ずつ確かめ直す。サブエージェントが返した呼び出しの道筋を、自分でコードと依存の手元の版のソース（ロックファイルの版）で辿り、守りの処理（その手前で弾く検査など）が無いかを見る。件数が多ければ、確かめ直しもサブエージェント（同じモデル）に、指摘の束ごとに任せる。そのときは「この指摘が成り立たない理由を探す」形で頼み、こちらの結論を渡さない。
   - 確かめられたもの → 載せる。タグに確かめた手段（コードで確認・依存のソースで確認・SQL で再現 など）を書く。
   - OS やブラウザーの実際の動きで決まり、読むだけでは決まらないもの → 起きる見込みと根拠を書いて載せ、タグに「実機は未確認」、「実機で確かめたいこと」にも1行入れる。資料（公式の文書）で決まるものは、資料を引いて載せる。
   - 道筋のどこかで守られていた・実際の操作で届かない → 落とす。読む人が疑いそうなものなら「確かめて問題なかったこと」に回す。
7. まとめる。同じ根の指摘は1件にし、「同じ根の症状」に書く。重さで節に分ける（下の「重さの分け方」）。節ごとに頭文字と連番の番号を振る（A1・B1…）。
8. レポートを `references/report-template.html` の組みで書く。指摘ごとに、利用者の操作と画面に出る文言（そのまま引く）から書き、内部の名前は「理由」と「場所」に回す。使わない節は、目次のリンクと上の件数の欄ごと消す。
9. `node <この skill のディレクトリ>/scripts/check-locations.mjs <レポートの HTML> <リポジトリのルート>` を流す。NG（終了コード 1。行がファイルの長さを超える）は、場所を読み直して直す。終了コード 2 は確かめられていないので、出た理由を直して流し直す。
10. アーティファクトとして出す（Claude Code では Artifact ツール。最初に出す前に、ツールが求める手順と skill を読む）。返答でリンクと結論を伝える。
11. 後で直したときは、アーティファクトを読み直し、該当する番号に対応の状況（タグ・「対応」の行・件数）を書き足して出し直す。初めて書き足すときは、ひな形でコメントにしてある「対応の状況」の欄をコメントから出す。

### 重さの分け方

節の名前と基準は、アプリと時期に合わせて変えてよい。基準は、利用者にとって何を失うかで決める。

| 節 | 入れるもの |
|---|---|
| <時期>の前に直したい | データを戻せない・ファイルを失う・止まったまま気づけない・見せないはずの物に届く。後の版では直せない（更新される側の版に要る）もの |
| ふつうの操作で踏む | データは失わないが、ふつうの操作で期待どおりに動かない |
| 意地悪をする人がいると踏む | アプリが想定する相手（同じ LAN の人・共有したファイルなど）が意図して踏ませるもの。漏れる物が重ければ一番上の節に置く |
| 軽いもの | まれにしか踏まないか、踏んでも困りごとが小さい |
| <OS>だけ | 大事な OS 以外でだけ起きるもの |
| マニュアルと文書 | マニュアル・README・設計の文書が、今の動きと食い違う |

## 合格条件

- 人が見る: 1件ずつの欄で書いた指摘には、利用者の操作と結果・理由・確かめ方・場所がある。一覧の行で書いた指摘には、何が起きるかと場所があり、確かめ方は節の note（「断りの無いものはコードで確認済み」）か、行のタグにある。確かめていない所は、タグと「未確認の所」に書いてある。件数の数字が節の中身と合っている。でっち上げの文言（画面に無い文）が無い。
- 機械が見る: `scripts/check-locations.mjs` が終了コード 0。
