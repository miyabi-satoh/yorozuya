# 3つの案から選んでもらう

## 仕事

見て差が分かる判断について、違いのはっきりした3つの案を作って1枚のページに並べ、ユーザーが選んだ案と理由を受け取って作業を続ける。人は3つの差を見比べるのは一瞬でできるが、1つの案の良し悪しや、多すぎる案からは選びにくいため。

## やらないこと

- 見た目に出ない設計（データの持ち方・同期の方式・API の形など）でページを作る — 見ても差が分からない。3案を損得の表で比べ、推奨を添えて返す。
- 一般的な形が1つに決まっているもの（よくある入力欄・定番の確認ダイアログなど）で3案を作る — 1案と拠り所で足りる。
- 細部だけが違う3案を出す — 差が見えず選べない。配置・構成・語の選び方など、方針の違う3つにする。
- 案を作る前に、拠り所を飛ばす — 案はどれも拠り所（よく知られたアプリの作法・プロジェクトの既存の画面・用語の決めごと）に沿わせる。利用者の指示ファイルや skill に UI の好みや拠り所が書いてあれば、それにも沿わせる。

## 出力

- 3つの案を並べたページ1枚。判断1つにつき1枚。同じ作業で判断がいくつも出たら、1枚に並べて一度に選んでもらう。
  - Claude Code で Artifact ツールが使えるなら、アーティファクトとして出す。選んだ案と一言の理由を残す欄を置き、結果は `db` の機能に残して `ArtifactData` で読む。作る前に `artifact-design` と `artifact-capabilities` の skill を読む。
  - アーティファクトを出せないエージェントでは、HTML ファイルを作ってブラウザで開き、選んだ案はチャットで返してもらう。
- 選ばれた案と理由を、そのプロジェクトの決めごと（`docs/ui.md`・用語の表・`decisions.md` など、プロジェクトが決めた置き場）に書いたもの。次に同じ種類の判断が出たとき、3案を出さずに済ませるため。

## 終わる条件

ユーザーが案を選び、選んだ案で作業を続け、その判断を決めごとに書いた。

## 止まる条件

次のときは推測で埋めずに止まり、ユーザーに聞く。

- 3つとも、ユーザーの条件や拠り所に合わないと分かったとき: 合う案が作れない理由を添えて、条件を確かめる。
- 選ばれた案が、既存の決めごとと食い違うとき: 決めごとのほうを書き換えるかを確かめる。

## 手順

1. 何を選んでもらうのかを1文で決める（例:「削除の確認ダイアログで、使われているテンプレートの警告をどこに出すか」）。ページの見出しにする。
2. プロジェクトの決めごとに、同じ種類の判断が既に書かれていないかを見る。書かれていれば、3案を作らずにそれに従う。
3. 違いのはっきりした3案を作る。1つは一般的な形（よく知られたアプリの作法）にし、残りの2つは方針を変える。
4. 案の見せ方は、作る手間の安い方を選ぶ。
   - 目安として、新しい画面は静的な HTML で再現する（動くコードがまだ無い）。
   - 今ある画面の手直しは、実物を3通りに直してスクリーンショットを撮る（データや状態の作りが既にあり、HTML で作り直すと手間がかかるうえ実物とずれる）。撮るのはブラウザの自動操作（Playwright など）で。
   - 文言だけの判断は、実際の画面の文脈（前後の項目・ボタン）に置いた形で見せる。文言だけを並べると、画面での読まれ方が分からない。
5. 3案を横に並べ（狭い画面では縦）、それぞれに短い名前と、ほかの案との違い・損得を1〜2行で添える。推奨を1つ示す。
6. ページを出し、返答の末尾で、ページを見て選んでほしいことを伝えてターンを終える。
7. 選ばれた案と理由を読み、その案で作業を続ける。理由が推奨と違えば、何を重く見たのかを読み取って、残りの作業にも当てる。
8. 選ばれた案と理由を、プロジェクトの決めごとに書く。

## 合格条件

- 人が見る: 3案が方針の違うものになっていて、ひと目で差が分かる。どの案も拠り所に沿っている。推奨が1つある。選ばれた結果が決めごとに書かれている。
- 機械が見る: 無い。
